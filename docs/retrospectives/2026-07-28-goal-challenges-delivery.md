# 目标挑战批次交付复盘（2026-07-28）

## 结论

本次延误不是单一代码问题，而是交付流程失控：同一功能先在 worktree 完成、又只把部分文件同步到正式目录，导致开发、测试、UI 分别检查了不同状态；同时出现重复短期会话和不必要的审批等待。之后以 `D:\carbs-king` 为唯一交付目录，所有“通过”必须有该目录中的证据。

## 发生了什么

1. 目标挑战完整实现先出现在临时 worktree；正式目录最初只有服务层和部分接线。
2. 因此服务专项可通过，但正式目录缺少个人页三赛道卡、创建/已完成/删除入口、全屏创建页、庆祝反馈等用户路径。
3. 后续检查还发现正式目录一度缺少 `goal_challenges` repository、存储文件与备份/清空接线；控制器已引用该仓库，存在运行时风险。
4. 重复的短期会话被创建后又停止，增加了沟通和 token 成本。
5. 测试会话发起了会写入缓存的编译检查，造成无业务价值的“等待审批”。

## 根因

- 没有先冻结“唯一正式目录 + 单一写入者 + 完整文件清单”。
- 将 worktree 的自测误当成正式交付证据。
- 先以服务层专项结果宣布可交付，未做集成完整性检查。
- 项目经理、全局负责人和短期工作会话的层级交接不够严格。
- 首次命令和验证命令过重，环境问题与业务问题没有及时分开处理。

## 固化规则

1. `D:\carbs-king` 是唯一功能开发、集成、测试、UI 验收和交付目录。
2. 每个业务批次只允许一名代码写入者；一个文件集合不得被并行会话同时修改。
3. 项目经理只向既有全局负责人派单；短期会话由直属负责人创建、验收和归档。
4. 新模块必须逐项确认：服务、仓库/存储、控制器/视图/主流程、备份/导入/清空、记录变更回调、持久化黑盒测试。
5. 测试和 UI 报告必须标注检查目录与结论范围；“服务通过”“静态预检通过”“用户路径点击通过”不得混用。
6. 不为了缓存、`compileall` 或临时输出向用户请求审批；已有无效审批应取消，不应让用户承担等待成本。
7. 环境失败只保留一次可复现证据；同类预检两次失败即停止重试并上报。

## 后续验收门槛

在本批次正式标记完成前，必须在 `D:\carbs-king` 完成：

- 目标挑战 UI/控制器/主流程的完整同步；
- repository、存储、备份、导入与清空的黑盒验证；
- 目标挑战和备份专项测试、相关编译检查、差异检查；
- 360×800 与大字体 UI 复检；
- 明确区分静态预检与实际点击验证。

## 不做的事

- 不把临时 worktree 的完成状态当作正式完成。
- 不新建同级负责人或重复业务会话。
- 不构建 APK、不发布、不推送，除非用户单独确认。
