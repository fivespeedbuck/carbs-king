# UI 规则沉淀

## 适用范围

适用于 `D:\carbs-king` 所有 Flet/Web 界面、移动端布局、表单、摘要卡片、详情页和验收截图。

## 长期防复发规则

1. 并排控件必须统一标签高度、基线、输入框宽高和间距，禁止同排控件上下顶歪。
2. 长中文标签默认单行处理，优先省略号或缩写；需要换行时只能放到独立说明区，不能挤压同排表单。
3. 手机宽度和大字体必须作为常规验收项，至少覆盖窄屏和放大字体两种视口截图。
4. 必查横向越界、页面滚动跳回、表单底部固定区是否被遮挡，任何溢出都视为阻断。
5. 必须走真实 Flet/Web 点击路径验收，不只看静态代码或渲染推断。
6. 每次 UI 问题都要记录 `现象 / 根因 / 修复 / 验证 / 预防`，先去重再追加。
7. 发布前必须确认 UI 阻断项清零，并清理预览端口和残留子进程。

## 验收建议

- 手机视口优先看 `390x844`、`430x860`。
- 大字体至少看一次系统放大后的真实浏览器效果。
- 重点检查首屏、展开状态、摘要卡片、底部按钮和固定条。

## 为什么这类 UI 验收会慢

- 先到的常常是加载态、浏览器提示、网络噪音，不一定是业务 UI 已坏。
- Flet/Web 经常没有稳定语义层，纯 DOM 或文本定位不总是可用。
- 真实问题要靠渲染结果和实际点击路径确认，不能只看代码或日志。

## 怎么更快做 UI 问题测试

1. 先清理旧端口和旧预览，避免把历史进程误当当前问题。
2. 先看一张截图，判断是白屏、加载态、浏览器噪音，还是业务页面。
3. 先锁定一个最小可复现路径，只验证一个入口和一个结果。
4. 优先用可见按钮、稳定坐标或明确语义点，不在整页 DOM 里大范围搜索。
5. 手机宽度和大字体只测关键页面，不一开始全链路铺开。
6. 入口一旦能打开，先确认空态，再确认有历史数据，再确认保存、删除、刷新。
7. 每次失败只改一个变量：视口、数据、按钮或预览环境，避免混杂。

## 代码层说明

- `Flet 语义层不稳定` 不是指业务逻辑错了，而是指页面在 Web 侧没有稳定暴露可定位的语义节点。
- 典型表现是浏览器里只能看到很少的可点击 `role/button`，或者只剩 `Enable accessibility` 一类占位节点。
- 结果就是自动化很难用标准 DOM 文本、按钮 role、label 精准点到控件，只能退回到截图和坐标点击。
