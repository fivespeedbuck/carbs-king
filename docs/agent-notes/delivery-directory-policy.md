# 碳水大王：唯一交付目录规则

更新时间：2026-07-28

## 结论

`D:\carbs-king` 是本项目唯一的功能开发、测试、UI 验收和交付目录。

不允许把 worktree 中的实现或测试结果直接当作项目完成证据。

## 执行规则

1. 项目经理只向现有全局负责人派单；负责人可创建短期工作会话。
2. 每一批业务代码在同一时间只能有一名写入者，直接写入 `D:\carbs-king`。
3. 全局开发负责人可以在自己的会话中协调、审查和汇总，但不能让 worktree 成为可交付开发副本。
4. worktree 仅允许只读研究或用户明确授权的隔离实验；不允许用于正式功能实现、测试结论或 UI 验收。
5. 测试负责人和 UI 负责人必须在 `D:\carbs-king` 读取代码、运行验证并报告结果；报告必须写明检查目录。
6. 没有 `D:\carbs-king` 的专项测试、编译和 UI 证据，不得标记“完成”“通过”或进入发布讨论。
7. 短期会话完成后，直属负责人负责审查、汇报并归档该会话；项目经理不跨层创建、替换或归档负责人会话。

## 验收前检查

- 当前工作目录是否为 `D:\carbs-king`。
- 实际 `git diff` 是否包含本批次改动。
- 专项测试、编译和 `git diff --check` 是否在正式目录执行。
- UI 报告是否明确为正式目录下的预检或真机结论。

## 集成完整性闸门

服务层测试通过不等于功能交付通过。每个新模块在进入测试/UI前，开发负责人必须在 `D:\carbs-king` 逐项证明：

1. 数据定义/服务文件已存在且可导入。
2. `AppRepositories`、存储文件和状态对象实际包含该模块需要的仓库/字段。
3. 控制器、视图和主流程引用的每个新接口都在正式目录存在。
4. 备份、导入、清空个人数据和记录保存回调已接线，或明确说明为何不需要。
5. 用正式目录实例做最小黑盒：构建默认仓库、创建一条数据、保存/重载、执行关键入口。
6. 再运行服务专项、相关集成/备份专项、`py_compile` 和 `git diff --check`。

不得以 worktree 的全量测试、仅服务层专项，或“文件看起来已经同步”替代上述正式目录证据。

## 测试与审批规则

- 测试负责人默认只运行不改写项目目录的命令；不要为 `compileall`、缓存或临时输出申请用户批准。
- 需要编译检查时优先使用单文件 `py_compile`，并使用已验证的 bundled Python 路径；不要依赖会话 PATH 中是否存在 `python`。
- 命令因环境/权限失败时，先区分“业务失败”和“工具写缓存/启动入口失败”；无业务价值的写入请求必须取消，不得要求用户批准。

## 这条规则解决的问题

worktree 可能已完成代码，而正式目录仍只有部分文件；若测试或 UI 在不同目录检查，就会出现“开发说完成、主目录没有、验收永远做不完”的假进度。所有可交付动作统一在正式目录执行，消除同步和目录漂移。
